# dogking-tools

![License](https://img.shields.io/badge/license-MIT-blue)
![ComfyUI](https://img.shields.io/badge/ComfyUI-custom%20node-green)
![Python](https://img.shields.io/badge/python-3.10%2B-yellow)

> **配套应用：[PromptVault](https://github.com/liao942287300-cyber/prompt-vault)**
> 离线图片提示词管理台 —— 纯原生 HTML/CSS/ES Module，零依赖，数据全存本地 IndexedDB。
> 本插件的「PromptVault 数据源」节点就是直连它。

ComfyUI 提示词/图片批量加载节点。读 [PromptVault](https://github.com/liao942287300-cyber/prompt-vault)
（或任何工具）导出的 `.txt` / `.csv`，按行输出提示词；也可以按顺序读一整个文件夹的图片，配合自动排队实现
**一条提示词（或一张图）跑一遍完整工作流**。

另外还有 4 个 **PromptVault 数据源节点**，不用导出文件，直接从 PromptVault 桌面应用实时拉
提示词 / 图片 / 词库（见下方「节点：PromptVault 数据源」）。

以及 1 个 **写回节点** —— 把提示词和生成参数（模型 / LoRA / 采样）嵌进 PNG 元信息，
出图后拖回 PromptVault 就能自动带词带参数（见下方「节点：提示词嵌入 PNG 元数据」）。

最后是 **数字人音频分段** —— 在波形上切段、每段配提示词和参考图，按段自动跑完整个音频
（见下方「节点：数字人音频分段」）。

配套的 **分段视频合并** 把每段生成的结果自动拼成一条完整视频，不用手工拼
（见下方「节点：分段视频合并」）。

再配一个 **上一段末帧续接** —— 读上一段成片的最后几帧当引导图，让分段之间接得上，
同时绕开「把采样结果接回自己的 guider」造成的循环连线（见下方「节点：上一段末帧续接」）。

## 安装

把整个 `dogking-tools` 目录放进 ComfyUI 的 `custom_nodes/`，重启 ComfyUI 即可。

```
ComfyUI/custom_nodes/dogking-tools/
```

两种装法：

```bash
# ① git clone（后续 git pull 就能更新）
cd ComfyUI/custom_nodes
git clone https://github.com/liao942287300-cyber/dogking-tools.git
```

② 从 [Releases](https://github.com/liao942287300-cyber/dogking-tools/releases/latest) 下 `dogking-tools-x.x.x.zip`，
解压到 `custom_nodes/` 下，**目录名保持 `dogking-tools`**（改成别的名字也行，但插件更新时容易搞混）。

不需要额外 `pip install` —— 用到的 `numpy` / `torch` / `Pillow` / `aiohttp` / `av` 全是 ComfyUI 自带（`av` 在 ComfyUI 官方 `requirements.txt` 里，17.0.0 起就是必需项）。
装完要**重启 ComfyUI**，只刷新网页不够 —— Python 节点要重新导入。

`soundfile` 是可选的加速项：装了读 wav / flac / mp3 走 libsndfile 更快，没装会自动退回 PyAV，再不行还有标准库 `wave` 兜底。`pytest` 只在跑测试时需要，普通使用不用装。

「选择文件」按钮在 Windows 上用 `ctypes` 直接调系统 `comdlg32.GetOpenFileNameW`，
**不依赖 tkinter** —— ComfyUI 的 `python_embeded` 是精简版，本身不带 tkinter。

## 三种模式

### 全部生成

从第 1 行跑到最后一行。每执行一次输出一行，计数器 +1，跑完后归零。

配合「自动连续」打开，点一次运行就能把整个文件跑完。

### 范围选取

只跑指定的行区间。

- 填 `20` → `40`，跑第 20 到 40 行
- **填 `40` → `20` 会自动纠正成 20-40**，不用管顺序
- 数值超过总行数时按总行数处理（比如文件只有 50 行，填 `1` → `999` 就是 1-50）

### 编号选择

固定输出第 N 行，**不递增**。每次执行都是同一行，适合反复调试同一条提示词。

---

## 自动连续怎么工作

节点每执行完一次，如果这个范围还没跑完，会通知前端排下一次队列。
前端在 `execution_success` 之后才排，避免队列错乱。

**手动停止（Interrupt）或报错时不会继续排**，计数器停在当前行，下次点运行从这里接着跑。

### txt

一行一条，空行自动跳过：


## 节点：Ripple 二采放大（dogking-tools）

配合 `ComfyUI-WepeNerd` 的 H3 Ripple 用：把 Ripple Clip 输出的 `ripple` 整体放大到二采尺寸，
**不用改第三方插件**。

```
Ripple Clip (ripple) → Ripple 二采放大 → Ripple Apply (ripple)
```

### 输入

| 参数 | 说明 |
| --- | --- |
| **ripple** | 接 H3 Ripple Clip 的 `ripple` 输出 |
| **模式** | `按倍数` / `按二采像素`。切到哪个模式，就只显示那个模式用的尺寸参数，另一个自动收起 |
| **放大倍数** | 按倍数模式：画布宽高 × 系数，默认 2 |
| **目标百万像素** | 按二采像素模式：跟二采流里的数学表达式一致，`ceil(sqrt(百万*1e6*宽/高)/32)*32` |
| **放大算法** | lanczos / bicubic / bilinear / area / nearest-exact |

### 输出

| 输出 | 说明 |
| --- | --- |
| **ripple** | 放大后的 ripple，宽高和 geometry 都改好了，直接接 Ripple Apply |
| **画面** | 放大后的窗口画面（含模型留边） |
| **宽度 / 高度** | 放大后的画布尺寸，一定是 32 的倍数 |

### 注意

- 画布宽高向上取 32 的倍数；内容区域按同比例放大，**留边比例不变**，构图不会歪。
- Ripple Apply 会按新的宽高建空 latent，guide 关键帧也用放大后的画面，二采不会尺寸对不上。
- 2 倍放大 = 4 倍像素。300 帧以上再 2 倍会明显吃内存，窗口短一点更稳。
- 跑完之后节点底部会显示这行：`480×864 → 768×1408（内容 768×1388）`。箭头前是原画布，箭头后是放大后的画布（喂给采样器、32 的倍数），括号里是画布中的**有效画面** —— Ripple Apply 提示里报的 `(768×1388)` 就是这个数。
- 宽高是各自向上取 32 的倍数，所以宽比和高比不一定完全相同（比如 768/480 = 1.60，1408/864 = 1.63），这是对齐导致的，不是算错。

## 节点：图片批量加载（dogking-tools）

分类：`dogking-tools` → **图片批量加载（dogking-tools）**

跟提示词节点同一套机制，只是数据源换成图片：每执行一次输出一张图，
`自动连续` 打开时前端会在本次执行结束后自动排下一次队列，直到跑完整个范围。

### 输入

| 参数 | 说明 |
| --- | --- |
| **文件夹路径** | 图片文件夹的完整路径。点下方「选择文件夹」按钮弹系统原生目录选择框；也可以直接填。相对路径按 `ComfyUI/input` 解析 |
| **排序方式** | `数字升序`（自然排序，`img2.png` 排在 `img10.png` 前面）/ `字母升序`（按文件名 a-z） |
| **模式** | `全部模式` / `范围模式` |
| **起始序号** | 仅范围模式显示 |
| **结束序号** | 仅范围模式显示，填 `0` 表示到最后一张 |
| **自动连续** | 打开后每跑完一张自动排下一张 |
| **手动列表** | 前端拖拽区自动写入（节点上隐藏，用户看不到）。想清空拖拽区就点缩略图上的 × |
| **重置计数** | 一次性按钮，点一下立即清零 |

> 参数会跟着模式变：选「全部模式」只留文件夹路径 / 排序方式 / 自动连续，
> 选「范围模式」才出现起止序号。节点高度自动收缩。

### 输出

| 输出 | 说明 |
| --- | --- |
| **图片** | 当前这张图，`[1, H, W, 3]` float32，值域 0-1，直接接 VAE Encode 之类的节点 |
| **当前序号** | 第几张（从 1 开始） |
| **总数量** | 这批一共几张 |
| **状态** | 例如 `第 3/100 张（全部模式 1-100）`、`第 3/100 张（范围模式 2-40）` |

节点底部会实时显示状态条，**中断或手动停止后一眼能看到跑到第几张**。

### 两种图片来源

1. **文件夹** —— 扫描文件夹里的 `.png / .jpg / .jpeg / .webp / .bmp / .gif / .tif / .tiff`，按排序方式排好
2. **拖拽** —— 把图片拖到节点的拖拽区，会自动上传到 `ComfyUI/input` 并追加在**文件夹扫描结果之后**（同一张图不会重复）

两种可以同时用：选一个文件夹，再额外拖几张图进来，一起按顺序跑。
排序只作用于文件夹扫描出来的那部分，拖进来的图保持拖入顺序。

拖拽区顶部显示 `共 N 张，当前第 M 张`，中间是缩略图网格，每张右上角的 × 可以移除。

### 范围模式

- 填 `20` → `40`，跑第 20 到 40 张
- **填 `40` → `20` 会自动纠正成 20-40**
- 超过总数时按总数处理（比如只有 50 张，填 `1` → `999` 就是 1-50）

### 注意

- 图片按 EXIF 方向自动转正（手机拍的竖图不会躺下），统一转成 RGB 三通道。
- 某张图读失败（文件损坏 / 格式不支持）**不会打断队列**：会输出一张 64×64 灰图占位，
  失败原因写在状态里，队列继续往下跑。
- 拖拽区拦住了 `drop` 冒泡，图片拖到节点上不会被 ComfyUI 当成工作流 JSON 解析。

## 节点：PromptVault 数据源（4 个）

分类：`dogking-tools`

不用再导出文件：**直接从 PromptVault 桌面应用实时拉数据**。在 PromptVault 里改提示词、
新建分类、加图，节点下一次执行立刻就能拿到。

> **PromptVault 必须开着。** 关掉之后节点会提示
> `PromptVault 未运行（试过 8765-8775），请先打开 PromptVault` —— 不抛异常、不打断队列，
> 已连线的图片口会输出 64×64 灰图占位，不会让下游节点崩。

### 四个节点

| 节点 | 用途 | 输出口 |
| --- | --- | --- |
| **PromptVault 图片+提示词（dogking-tools）** | 选图 + 取它的提示词 | **图片 / 提示词** |
| **PromptVault 词库（dogking-tools）** | LORA 触发词 / 编辑指令 / LLM 系统提示词 | **内容** |
| **PromptVault 资产图（dogking-tools）** | 选 1 张资产图 | **图片** |
| **PromptVault 资产图批量选择（dogking-tools）** | 选多张资产图，每张一个输出口 | **图1 … 图9**（无固定口） |

> 输出口已按需求精简：负向 / 参数 / 序号 / 总数 / 状态这些**不再占输出口**。
> 状态提示（`超 8 张` / `N 张已失效` / `短边 → 尺寸`）改由节点底部的状态条显示。

### 内嵌面板（4 个节点共用）

拖出节点就带一个 600px 高的面板，**直接在节点里点选**，不用记分类路径：

| 操作 | 说明 |
| --- | --- |
| **展开 / 收起面板** | 按钮切换。收起后节点只剩状态条（`已选 4 张：正面 / 侧面 …`） |
| **拖动节点右下角** | 面板高度**跟着变**（拖多大就多大，最小 180px），网格能一屏看更多 |
| **分页** | 首页 / 上一页 / 下一页 / 末页，每页 20 / 40 / 80 可选 |
| **搜索** | 300ms 防抖；图片匹配名称 + 提示词正文，资产图匹配名称 / 分类 / 项目 / 备注 |
| **点选** | 点卡片切换选中态；Shift 连选区间；跨页保留 |
| **图片显示** | 缩略图按 `contain` 完整显示（不裁切），非正方形的图四周会有留白 |
| **清空 / 取消 / 确定** | 见下表。**点选只是草稿，点「确定」才写回节点** |
| **随机多选** | 工具条「随机抽 N 张」，N 由节点上的「随机数量」决定（**上限 200**） |
| **删除单张** | 选定态里每张有「移除」；删中间项会弹确认框（见常见问题） |

**底部按钮：只有节点 4 有「确定」**

| 节点 | 底栏 | 点选后 |
| --- | --- | --- |
| 节点 1 / 2 / 3 | 只有「清空」 | **立即生效**（写回节点） |
| **节点 4（批量选择）** | 清空 / 取消 / 确定 | 只是草稿，点「确定」才生效 |

节点 4 单独要确认，是因为它是**动态输出口** —— 每张图占一个口，点一下就写回会让
输出口跟着疯狂增删，连带断掉用户已经连好的下游连线。其余三个节点只吐固定数量的口，
实时写回没有副作用。

> 按钮已加大（32px 高、最小宽 72px），不容易点空。

**选定状态（点确定之后）**

- **节点 3**：网格收起，只显示已选的那张大图（**加载原图，不是缩略图**），
  图片区占面板高度约 **90%**（名称 / 尺寸 / 「更改图片」压在同一行，不浪费垂直空间）。
  点「更改图片」→ 回网格并进入**替换模式**（工具条提示「点一张替换当前图片」），
  点任意一张 → **直接替换并回到预览态**，不用自己找「哪张是当前选中的」。
- **节点 4**：网格收起，显示已选卡片（每张 **229×229** + 左上角序号 + 名称，
  比网格里的 96px 大一倍多，方便核对），
  每张下面两个按钮：
  - **更换** —— 只替换这一张：回网格 → 顶部提示 `正在替换第 2 张，点一张替换`
    → 点任意一张 → 只换第 2 张，其他不动，输出口数量不变
  - **移除** —— 删掉这一张（删中间项会弹前移确认）
  底部「**重新选择**」→ **清空已选**并回网格重挑（widget、输出口、面板选中三处一起清），
  同时退出替换模式、工具条恢复成正常的筛选面包屑。

### 节点 1：图片+提示词

**参数**

| 参数 | 说明 |
| --- | --- |
| 服务地址 | 留空 = 自动发现（探 `8765-8775`）；也可填 `127.0.0.1:8766` 强制指定 |
| 分类 | 一级分类；「全部」= 不筛选。**选一级会自动包含其下所有二级分类的图** |
| 二级分类 | 只显示叶子名（`写实摄影`）；面板工具条显示完整路径（`风格 / 写实摄影`） |
| 选择模式 | `单选` / `批量选` / `随机多选` |
| 输出方式 | `一次性全部输出`（一次吐整个 batch）/ `排队输出`（每次一张） |
| 随机数量 | 1–200，默认 4，仅「随机多选」可见 |
| 自动连续 | 排队输出时，每跑完一张自动排下一次队列 |
| 已选 | 隐藏字段，随工作流保存，**不要手改** |

**选择模式决定哪些参数可见**

| 选择模式 | 输出方式 | 随机数量 | 自动连续 |
| --- | --- | --- | --- |
| 单选 | 隐藏 | 隐藏 | 隐藏 |
| 批量选 | 显示 | 隐藏 | 排队时显示 |
| 随机多选 | 显示 | 显示 | 排队时显示 |

**一次性输出的上限是 32 张**（32 × 1024² × 3 × 4B ≈ 400MB，8G 显存安全）。
超过 32 张会**自动降级为排队输出**，并在状态条里明确告知：

```
清单 50 张超过一次性输出上限（32），已自动改为排队输出（本次输出第 1 张）
```

不静默切换、不截断、不报错拒绝执行。

尺寸不一致时以**第 1 张**的宽高为基准做 letterbox（等比缩放 + 居中补边）。
填充用的是**边缘像素复制**而不是黑边 —— 纯黑是高对比区域，下游 VAEEncode / IPAdapter
会把黑条当图像内容编码进 latent。补过边的张数会写进状态：`12 张已补边对齐到 1024×1536`。

### 节点 2：词库

参数只有三个：**服务地址 / 数据源 / 已选**。

词库**没有分类维度**（LORA 触发词、编辑指令、系统提示词都是平铺的），所以不做两级联动。
面板是卡片视图，正文为空时显示「（无触发词）」。

**只能单选**。万一清单里有多条，状态条会说明
`词库节点仅支持单选，已取第 1 条（共选 2 条）`，不会静默截断。

### 节点 3：资产图（单张）

参数：**服务地址 / 项目 / 分类 / 短边尺寸 / 已选**。

「项目」在「分类」**上面**：先选项目，再看这个项目下有哪些分类。

资产图只有 `分类` / `项目` 两个**平级字符串维度**（不是两级分类），所以是两个独立下拉、
互不联动。「项目」里的 `未分项目` 表示没有填项目的资产图。

面板是**两态**：网格选择 → 点「确定」→ 预览（大图 + 名称 + 尺寸），
点「更改图片」回网格。详见上面的「选定状态」。

### 节点 4：资产图批量选择（动态输出口）

参数：**服务地址 / 项目 / 分类 / 短边尺寸 / 已选**。

和节点 3 一致：**「项目」在「分类」上面** —— 先选项目，再看这个项目下有哪些分类。

**8 个口全是图片口，没有固定口**（名称 / 总数 / 状态已删，「输出模式」也删了 ——
只剩独立输出口一种行为）：

`图1` / `图2` / … / `图9`，
按已选数量增删（最多 9 个），每口输出 `[1,H,W,3]`，各自保持原尺寸。

每个口的标签是 `图N · 名称前8字`（如 `图2 · 角色四视图-侧面`），不用去数序号。

选超过 9 张时只填前 9 个口，状态条提示
`已选 12 张（只输出前 9 张）`。

**确定后进选定状态**，可以只改其中一张 —— 见上面「选定状态」。

### 「项目 / 分类」下拉的选项从哪来（节点 3 / 4）

这两个下拉的选项**不是固定的**，是从你的资产图列表里聚合去重出来的 ——
PromptVault 的桥接口没有「资产分类列表」这种接口，只能拉一遍资产图再算。

所以：

| 你做了什么 | 下拉会变吗 |
| --- | --- |
| 在 PromptVault 里新建项目 / 分类 | **展开面板时自动刷新**，会变 |
| 改了某张资产图的分类 / 项目归属 | 同上 |
| 只是换选中的图 / 改短边尺寸 | 不用刷新 |

节点底部还有一个「**刷新分类**」按钮，是手动兜底 —— 面板已经展开时想强制重拉就点它。

> 刷新失败（PromptVault 没开）时会保留旧选项，不会把下拉清空。

### 短边尺寸（节点 3 / 节点 4）

| 值 | 行为 |
| --- | --- |
| `0` | 输出原图，不缩放 |
| `1024`（**默认**） | 短边缩到 1024，长边等比 |
| 其他 `>0` | 把**短边**缩放到该值，长边等比，**不裁切、不补边** |

> 默认 1024 是因为下游大多按 1024 级别工作，4K 原图直接喂进去又慢又吃显存。
> 要原图填 `0`。

例：`3840×2160` 的图填 `1024` → 输出 `1820×1024`。

节点 4 选多张不同尺寸的图时，**每张各自缩到短边 N，保持各自的宽高比**
（不是统一成一个尺寸 —— 统一意味着拉伸或裁切，两者都会毁图）。

状态条会写明实际结果：`已输出 1 张（图片 (28)） · 短边 1024 → 1820×1024`。

### 常见问题
**Q：打开工作流时面板为什么是收起的？**
A：刻意如此。打开工作流时用户只有两种动作 —— 直接跑（清单在隐藏 widget 里，收起不影响），
或者改选择（必然要点开面板）。收起正好省掉一次无用加载，也不会一次拉几十张缩略图。
状态条会显示 `已选 N 张：… · 点击展开`，点一下就能看到。

**Q：为什么删掉中间某张，断的是最后一个口的连线？**
A：输出口是**位置语义**，不是 id 语义 —— 第 i 个口装的是清单里的第 i 张。
删掉中间某张后，后面的图会**整体前移**，所以尾部那个口被移除、它的连线断开。
删除中间项时会弹确认框说明这一点；删最后一个则不打扰（只断它自己）。

**Q：一次性输出为什么最多 32 张？**
A：显存。一张 4K 图 decode 成 float32 约 100MB，32 张已接近 3GB。超过就自动改排队输出，
状态条会说明原因。

**Q：节点报「PromptVault 未运行」怎么办？**
A：先打开 PromptVault 桌面应用。它会在 `8765-8775` 里挑一个端口开本地只读服务，节点会自动探到；
也可以在「服务地址」里手动指定。此时已连线的图片口会输出灰图占位，不会让下游节点崩。

**Q：老工作流里的 4 个 PromptVault 节点怎么变红了？**
A：v2 把旧的「提示词 / 图片 / 图片+提示词 / 词库」4 个节点**硬删**了，换成了上面这 4 个。
旧节点会显示为缺失（红色），替换成新节点重新选图即可。

## 节点：提示词嵌入 PNG 元数据（dogking-tools）

分类：`dogking-tools`

**把提示词写进 PNG 的元信息里，再导回 PromptVault 就能自动带词。**
出图 → 嵌入 → 拖进 PromptVault，正向 / 负向两栏自动填好，不用手抄。

### 为什么它自己存文件

ComfyUI 节点之间传的是**纯张量**，不带任何附带信息；PNG 的文本块只在**写文件那一刻**
产生。提示词只要停在某个节点的 widget 里，下游接哪个保存节点都不会把它写进图里 ——
所以这个节点**自己往 `ComfyUI/output/` 写一份带元数据的 PNG**，同时把图片原样透传。

> ⚠️ 它**替代**保存步骤。后面再接 `保存图像`（SaveImage）会多出一份没有提示词的拷贝。

### 输入

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| **图片** | IMAGE 口 | 要写元数据的图；原样透传，不改尺寸不改像素 |
| **正向提示词** | STRING 口（只接线，**必接**） | 接上游的字符串输出，写进 `parameters` 块 |
| **负向提示词** | STRING 口（只接线，**可选**） | 接上游的字符串输出，写成 `Negative prompt:` 行；**不接就不写这一行**，不会报错 |
| **文件名前缀** | 字符串 | 默认 `PromptVault`，自动补 `_00001_` 序号；支持 `子目录/名字` |

两个提示词口是 **forceInput**：节点上只有插口，没有文本框。词都在上游节点里
（PromptVault 节点的「提示词」输出、`PrimitiveString`、任意字符串节点）；
再摆两个编辑框只会让人以为手填的值也会被写进去。

### 输出

| 输出口 | 类型 | 说明 |
| --- | --- | --- |
| **图片** | IMAGE | 原样透传，给下游预览 / 其他处理 |

执行完**节点上会直接显示刚存的那张图**（和「保存图像」一样的预览框，批量时显示第一张），
标题栏右侧还有个蓝色小标签写着文件名（如 `PromptVault_00001_.png`）；完整信息
（正向多少字、负向多少字、失败原因）在 ComfyUI 控制台里。

### 写进去的是什么

只写 **一个** 文本块 —— `parameters`，内容按 A1111 规范：

```
银白发猫娘, 蓝白女仆装, 金铃铛蝴蝶结
Negative prompt: lowres, bad anatomy, extra limbs
Steps: 28, Sampler: dpmpp_2m, Schedule: karras, CFG scale: 6.5, Seed: 123456789, Size: 832x1216, Model: dreamshaper_8.safetensors, Lora_1: detail-tweaker.safetensors:0.8, VAE: vae-ft-mse.safetensors, Clip skip: 2
```

### 生成参数是自动抓的

不用多接一排口。节点读 ComfyUI 的 `hidden: {"prompt": "PROMPT"}`（本次执行的
API prompt 全图），按字段名扫一遍：

| 字段 | 从哪来 |
| --- | --- |
| 模型 | `ckpt_name` / `unet_name`（Flux 走 UNETLoader）/ `model_name` |
| LoRA | `lora_name` + `strength_model`，多个就 `Lora_1` `Lora_2`… |
| VAE | `vae_name` |
| 采样 | `steps` / `cfg` / `sampler_name` / `scheduler` / `seed`（或 `noise_seed`）/ `denoise` |
| Clip skip | `stop_at_clip_layer` 取绝对值（A1111 记的是层数，ComfyUI 存的是负偏移） |
| 尺寸 | **实际存下来的那张图**，不是 EmptyLatent 的设定值 |

识别只看字段名和 class_type 关键词，不绑死节点类 —— `KSampler`、`KSamplerAdvanced`、
`SamplerCustomAdvanced` + `KSamplerSelect` + `RandomNoise` + `ManualSigmas` 这套组合
都能收。多个采样器（hires fix）只取节点 id 最小的那个主采样；链接进来的值
（比如 seed 接了别的节点）会跳过、不瞎猜。

几点要说清：

- **步数有兜底**：新版 ComfyUI 的主力是 `SamplerCustomAdvanced` + `ManualSigmas`，
  **整张图里没有 `steps` 字段**，步数藏在 sigmas 串里 —— 10 个 sigma 值 = 9 步，
  节点会数出来。只认 `steps` 的话这类工作流（Qwen / Flux 基本都是）一个参数都写不出。
- **参数行必须以 `Steps:` 开头**。PromptVault 靠这个标记认定「从这儿起是参数」，
  没有它后面的内容会被当成负向词的延续。真拿不到步数时，这一行改写成**独立文本块**
  （key = `params`），由 PromptVault 的兜底分支收进「参数」栏，不会污染负向词。
  参数栏里会显示成 `params: Size: 832x1216, Lora_1: ...`，多一个前缀是正常的。
- 只有 `Size` 没有别的字段时**不写参数** —— 纯裁切 / 放大的图没有采样信息，
  写一行 `Size: 512x512` 只是噪音。这种情况标题栏 badge 会显示「无参数」。
- 只有 `denoise ≠ 1` 时才写 Denoise，默认值写了只是噪音。
- **已知限制**：条件分支（`easy ifElse` 这类）里挂着的多个 LoRA 会被**全部列出** ——
  API prompt 只记录图的结构，不记录实际走了哪条分支，所以节点无从判断。

PromptVault 的 `js/png-meta.js` 按这个顺序识别：`parameters` → `prompt`/`workflow`
（ComfyUI JSON）→ `comment`（NovelAI）→ 显式负向键 → 其余兜底。写标准 A1111
格式能让它**精确**拆出正向和负向，不依赖「靠 worst quality 这类词猜哪段是负向」
的启发式。

反之**故意不写** `positive` / `workflow` 这些块：`positive` 会落到兜底分支被拼进
「参数」栏，`workflow`（ComfyUI JSON）会把整段 JSON 塞进「参数」栏 —— 都是脏数据。

中文提示词用 **iTXt**（PNG 里唯一声明 UTF-8 的文本块），不是 `tEXt`（latin-1，中文会炸）。
注意 iTXt 的**值**是 UTF-8，**key 仍是 Latin-1** —— 所以块名只能是 ASCII 的
`parameters` / `params`，写成中文会让 Pillow 抛 `UnicodeEncodeError`、整张图存不下来
（节点内部对这种情况有 ASCII 兜底，不会真的失败）。

### 注意

- 文件保存在 `ComfyUI/output/`，`文件名前缀` 支持 `%date%` / `%width%` 这类占位符
  （走 ComfyUI 自己的 `get_save_image_path`，编号规则和 `保存图像` 一致）。
- 正向、负向都为空时仍然存图，但**不写文本块**，标题栏标签会带「空词」，提示词管理里
  这张图会落到「无提示词」。
- 每次执行都会新存一个文件（不命中缓存），连跑 10 次就是 10 个文件。

## 节点：数字人音频分段（dogking-tools）

分类：`dogking-tools`

**一段音频切多段，每段一个提示词，按段自动跑完整个工作流。**
数字人视频一次只吃几秒音轨，以前要在外面反复用「音频裁剪」改起止时间、一次次重跑；
这个节点把分段表存在节点里，配一次就够。

### 面板

```
（节点顶部空白区，画在画布上）
全局参考图  2/6                                      短边 1024 px
[img] [img] [＋]                                        ← 3 列 × 2 行，共 6 个槽
[＋]  [＋]  [＋]

（下方面板）
全局提示词
[________________________________________________]
[选择音频] [重新载入]  voice.wav · 0:32.08   [▶ 试听第 2 段]
┌──────────────────────────────────────────────────────┐
│ 0:00        0:05        0:10        0:15             │ ← 刻度
│ 1     ┃ 2         ┃ 3(选中)     ┃ 4          ┃ 5     │ ← 段号 + 切点(带抓手)
│ ▁▂▅▇  ┃ ▅▂▁▃▅▇█  ┃ ▇▅▃▁▂▄▆█▆  ┃ ▄▂▁▂▅▇    ┃ ▅▇█   │ ← 波形（按段着色）
│ 5.00s ┃ 5.00s    ┃ 3.20s      ┃ 3.00s      ┃ 2.80s  │ ← 段长
└──────────────────────────────────────────────────────┘
━━━━━━━━●────────────────────────────────  00:09.80 / 00:32.08   ← 播放进度条
● 顺序 · 第 2 / 5 段 · 5.00s          [ 2 ] [跳到] [↺ 回到第 1 段]   ← 输出状态
[加切点] [自动等分] 5 秒/段  [清空分段]
① 00:00.00–00:05.00  5.00s  [提示词____________] [＋图]  ×
② 00:05.00–00:11.24  6.24s  [沿用全局提示词____] [图3]  ×   ← 本段有自己的 3 张
```

看图的三个层次：**奇偶段底色交替** + **每条切点带中间抓手** + **段号 chip / 段长标注**。
选中段蓝色（顶部 3px 状态条 + 底部色块），试听中的段绿色（波形也变绿，段号显示 ♪，
列表里那一行同时变绿并自动滚到可见位置）。

**输出状态行**右边的三个控件：

| 控件 | 作用 |
| --- | --- |
| `[ N ]` 数字框 | 想从第几段开始。跟着当前高亮的段自动变，正在输入时不抢你的字 |
| `[跳到]` | 把顺序游标设到 N，**下次执行从第 N 段开始**。已生成的 `seg_000N.mp4` 一个都不动 |
| `[↺ 回到第 1 段]` | 游标归零，等于从头跑（配合「开始时清空旧片段」会把累积目录也清掉） |

面板被拖窄时这三个控件会自动换行，**状态文字永远完整显示**（实测 320 / 400 / 620px 都不截断）。
按钮也不会再被挤成「选/择/音/频」竖排。提示信息走独立一行、4 秒后自动消失 ——
以前它直接覆盖文件名那一栏，点一次「回到第 1 段」文件名就没了。

`[跳到]` 是给「中途强杀」「想补某一段」用的。顺序游标在**开始执行时**就推进落盘，
所以跑到第 2 段被强杀后再启动，会直接从第 3 段开始、第 2 段永久缺失，最后合并报
「缺第 2 段」。这时把数字框填 2 点一下 `[跳到]` 就行，不用手改 `state.json`。
注意**单段模式补跑不写累积目录**（段数=1 走独立文件），补段必须用顺序模式 + 跳到。

**播放进度条**在波形下面：绿色填充 + 圆形拖头表示播到哪儿，右边写「当前 / 总长」，
轨道上还有和切点一一对应的细刻度。整条可点、可拖（边拖边跳），拖到别的段时
选中段和「当前段」跟着换 —— 边听边找位置不用来回点。

每段行里除了起止时间，还单独有一列**秒数**（`5.00s`）—— 4 分半的音频上，
光看 `00:12.94–00:20.11` 是心算不出这段多长的。

操作：

| 动作 | 效果 |
| --- | --- |
| 单击段内 | 定位光标（虚线）+ 选中这一段 |
| **拖任意一条切点线** | 两侧段一起跟手（永远共边，不会拖出空洞或碎段） |
| **双击段内** | 在该位置切一刀 |
| 点段的时间 | 试听该段（播到段尾自动停，按钮上写着「第几段」） |
| 点 / 拖进度条 | 跳到该位置；正在放就接着放，跨段时高亮跟着换 |
| 「加切点」 | 在光标那刀；没定位光标就切选中段正中 |
| 「自动等分」 | 按「秒/段」等分**选区**里的音频，之后再手动微调 |
| 段尾「×」 | 删掉这一段，并入相邻段（不留空洞） |

### 先裁选区，再分段

头尾不要的部分不用切、也不用跑完再删：**波形最左 / 最右那两条青线就是选区边界**。

- 往里拖 = 裁掉头/尾。被裁掉的部分**重压暗 + 斜纹**，一眼看出不参与；拖过里面的切点
  会把那些段一起吃掉，不会卡在第一条切点上过不去
- 选区存在 `分段数据` 的 `range` 里，点「清空分段」不会把裁好的头尾一起清掉
  （清完还是这块选区，接着点「自动等分」即可）
- 「选区取整段」一键恢复，把之前裁掉的都拿回来（切点不会回来，只恢复范围）
- 选区内**除当前段以外的段都会压暗**，加上选中段那圈 2px 亮边框 ——
  多段的时候也能一眼看出正在看哪一段；试听中则是绿色（边框 + 波形 + 列表行同步）

> 只有选区内的时间会被切成分段，所以夹在头尾的多余内容根本不会进入生成队列。

### 参考图（全局 / 每段）

**全局参考图不在面板里，画在节点顶部那块空白上**：6 个槽位（3 列 × 2 行），点空槽就弹系统多选框，
可以按住 Ctrl 一次选好几张（一次选 6 张不用点 6 次）。有图以后槽位右上角出现 `×` 可以单张删，
点图本身是替换那一张。

> 为什么画在那儿：这节点有 18 个输出口，litegraph 把 widget 区起点压到「标题 + 输出口总高」，
> 左边自然空出 360px。DOM widget 挪不上去（容器 top 由 litegraph 控制），所以直接用节点自己的
> canvas 画 —— 那块区域本来就什么都没有。

标题行右侧的 **短边**（默认 `1024`）点一下会弹输入框：

| 值 | 效果 |
| --- | --- |
| `1024`（默认） | 每张图按**短边**缩到 1024，长边等比。3000×2000 → 1536×1024；800×1600 → 1024×2048 |
| `0` | 原图不缩放 |

只缩不裁 —— 裁切会切掉内容，补边会引入黑条，两者都会被 VAE 当成画面内容编码进去。
放大也做（800 的短边配 1024 就放大），这样「换了张图尺寸就变」不会成为意外。
长边另有一个 4096 的硬上限，超过再缩一档，防止 6 张 4K 图一起进来把显存吃干净。

**每段还能单独指定参考图**：段行里那个 `[＋图]` 按钮。点开在下面展开一行小槽位，
同样是 6 个、同样是多选。规则只有一条：

> **本段只要有任意一张图，就整组覆盖全局**（不是逐张合并）。

为什么是整组覆盖：混合会造出「第 2 张换成了新图、另外 5 张还是全局的」这种半换状态，
对接镜头切换毫无用处，而且完全没法预期。要「这一段的参考换一批」就是换一批。
段行按钮会显示张数并变绿（`[图3]`），一眼看出这段没在用全局。
「清空本段」回到沿用全局。

**输出**：节点右边多了 6 个 IMAGE 口（`图1`…`图6`），每次执行吐**当前段**该用的那几张，
不足的位置是空（`None`）。没接线时 ComfyUI 根本不读它，也不会有开销。

> 空位给 `None` 而不是灰图：灰图会被当成真实参考送进模型，生成结果莫名其妙带灰，
> 而且查不出来。宁可空着 —— 接了下游又没设第 N 张时，报错比悄悄污染好。

全局参考图和短边限制存在隐藏字段 `参考图数据` 里（`{"short":1024,"images":[...]}`），
每段的图存在 `分段数据` 的 `segments[i].images` 里 —— 都跟着工作流一起保存。

### 输入

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| **音频** | AUDIO 口（可选） | 接了就用它，忽略「文件路径」 |
| **文件路径** | 字符串 | 本机音频文件；也可以点面板上的「选择音频」自动填 |
| **前置重叠帧**（默认 0） | 本段音频往前多带 N 帧（24fps）上一段的尾巴。接了「上一段末帧续接」时必须填成和画面裁剪起点一样（22 帧方案 → 22），否则每段音画错位、口型越跑越快。填 0 = 不前置 |
| **全局提示词** | 多行文本 | 所有段共用的提示词 |
| **分段数据** | 隐藏字段 | 面板自动生成的 `{range:{start,end}, segments:[{start,end,prompt,images?}]}`，不用手改 |
| **参考图数据** | 隐藏字段 | 面板自动生成的 `{short:1024, images:[路径…]}`（全局参考图 + 短边限制），不用手改。**排在所有 widget 最后** —— 中间插新控件会让老工作流的每个值都错一位 |
| **输出模式** | 单段 / 顺序 | 见下 |
| **当前段** | 整数 | 单段模式用；顺序模式忽略 |
| **自动连续** | 开关 | 顺序模式下每跑完一段自动排下一段 |

### 输出

| 输出口 | 类型 | 说明 |
| --- | --- | --- |
| **音频** | AUDIO | 当前那一段（已按秒切好） |
| **提示词** | STRING | **已经合并好的最终提示词**：该段写了独立词就出独立词，没写就出全局词 |
| **段序号** | INT | **这次输出的是第几段**（1 起）：单段模式下等于「当前段」，顺序模式下跟着游标走 |
| **段数** | INT | **这次要产出几段**：单段模式恒为 **1**，顺序模式才是总段数 |
| **本段时长** | FLOAT | 秒 |
| **选区音频** | AUDIO | **整条选区**（裁掉头尾之后），不是当前段 —— 接给「分段视频合并」压音轨 |
| **图1 ~ 图6** | IMAGE | 当前段该用的参考图（段内有图就整组覆盖全局），按短边限制缩过。没图的位置是空 |

> **音频只保留两个口**：当前段、整条选区。段 2 以后「音频」会往前多带 22 帧（给被钉住的
> 引导画面当时间基准），比裁过的画面长 0.917 秒。预览要把两边**一起**裁：
>
> | 预览链路 | 节点 | 值 |
> | --- | --- | --- |
> | 画面 | `ImageFromBatch`（预览裁掉引导） | 批次索引 **22** |
> | 音频 | `TrimAudioDuration`（预览音频裁掉前置） | start_index **0.9167** |
>
> `0.9167 = 22 ÷ 24`，必须等于这里「前置重叠帧」除以 24，两个数一起改。
>
> **为什么要裁**：引导那 22 帧是模型按上一段尾巴**重画**的（AddGuide 走条件、不是硬锁），
> 实测这 22 帧整体偏亮 —— 上半区过曝像素占比 8.3%，正常段只有 5.4%，肉眼看是头发和
> 背景蒙了一层白雾，到第 23 帧才落回正常。不裁掉，预览开头就一直"闪白光"。
> 成片那边一直是裁的，所以成片没有这个问题。

> 「全局提示词」原来还单独有一个输出口，已经删了 —— 两个口摆在一起，接到那个就等于
> 把段内的独立词全顶掉，「覆盖」功能直接白做。现在只要接「提示词」这一个口，
> 该用哪个由节点自己判断。

### 两种输出模式

- **单段**：`当前段` 指哪段就出哪段，不推进游标。调试某一段时用。
- **顺序**：每次出下一段，跑完一轮自动归零。开了「自动连续」就一路跑到底。

单段模式**只认 `当前段` 这个数字**（面板高亮只是显示）。点面板上的段、改这个数字，
两边会互相同步；打开工作流时也是按这个数字恢复高亮。

> 「段数」报的是**本次任务规模**，不是切了几段。单段模式跑一次只出一段，所以是 1 ——
> 拿它当循环次数 / 批量上限时，不会被「切了 8 段」牵连。要知道出的是第几段，接「段序号」。
> 面板状态行上的 `第 3 / 8 段` 用真实总段数（给人看），和这个输出口无关。

游标存在 `state.json`（按节点 id）。**重置条件是「切点变了」**：
只改某段的提示词不会重置，否则改一个错字就得从头再跑一遍。

**想手动回到第 1 段**：面板上那段状态行右边有「↺ 回到第 1 段」按钮 ——
清掉游标（同时把「当前段」改回 1），切点、选区、提示词一个都不动。
不用改切点、也不用删了节点重搭。

那行状态本身也够用：`顺序 · 第 4 / 8 段 · 15.00s`（14px），
模式、进度、本段时长一次看完。**节点标题栏不再挂 badge** ——
那几个数字又小又挡事，挪进面板里了。

> 顺序模式用的是独立事件（`dogking-tools.audio.next`），和「提示词批量加载」的
> `dogking-tools.next` 分开 —— 两个节点同时在工作流里时不会互相触发排队。

### 排队跑多个项目

队列里可以同时排两个项目（A 跑着，你把界面改成 B 再点运行），但有两处**必须**知道：

**1. 游标按「节点 + 音频」隔离**，不是共用一条。
同一个分段节点上换一段音频做另一个项目，两边进度各走各的：A 跑到第 3 段时排 B，
B 从自己的第 1 段开始，回头再跑 A 还是第 4 段。

用的是**音频文件名**（不含目录、不含扩展名）：
`C:\music\归期.wav` 和 `D:\备份\归期.wav` 算同一个项目。
所以换项目要换音频文件 —— 这是最自然的区分，不用多填一个参数。

> 升级前的游标记在纯节点 id 上。第一次跑时如果分段表签名还对得上（= 同一个项目），
> 会自动搬到新 key 上，跑到一半的进度不会归零；签名对不上（= 另一个项目）就原样留着，
> 不动它。

**2. 自动连续会停下来，而不是拿新参数去跑**
自动连续提交的是**当前界面**的图，不是刚跑完的那一份。所以每跑完一段，前端会拿后端的
「项目指纹」（`音频文件名|段数`）和界面比一下：

| 情况 | 行为 |
| --- | --- |
| 界面没动 | 照常排下一段 |
| 换了音频 / 重新等分 | **不排**，面板提示「界面参数已改动，自动连续已暂停 —— 点运行继续」 |
| 只改了提示词 / 参考图 | 照常排（改词是常态，不该把自动连续停掉） |

不加这道拦截的话，A 跑到一半你切到 B，自动连续会把 B 的参数拿去跑「A 的下一段」——
段数、参考图、提示词全串，最后合并报缺段，而且看不出是哪一步错的。

**3. 两个项目记得用不同的「任务名」**（合并节点那个参数）
片段目录按任务名分（`output/dogking_concat/<任务名>/`），任务名相同就会互相覆盖 ——
A 的段 1 会清掉 B 的文件。

正确姿势：`顺序模式` + **关掉自动连续** → 排 A 的 job → 改界面 → 排 B 的 job。
两边都按自己的游标跑各自的第 1 段。

### 波形是真的，切也是真的

波形由后端解码生成（`/dogking-tools/audio_peaks`），切音频用的是**同一套音频数据**。
所以波形上标的 5.00 秒，切出来就是 5.00 秒 —— 不会出现「看着对齐、出来差两帧」。

浏览器解码各家格式行为不一致（mp3 时长有偏差、m4a 看系统），这也是走后端的原因。

**解码链：soundfile（libsndfile）→ PyAV → 标准库 wave**，三级依次降级。
故意**不用 `torchaudio.load()`** —— 新版 torchaudio 把解码外包给 torchcodec，
而 `python_embeded` 里的 torchcodec DLL 常和 torch 版本对不上，一调用就弹
「无法定位程序输入点 torch_dtype_float8_e8m0fnu 于 libtorchcodec_image.dll」，
那个模态框不点掉，请求线程一直卡着、面板永远停在「解码中…」。
mp4 这类容器里的音轨也走 PyAV，能直接抽出来。

### 注意

- 支持的格式：wav / mp3 / flac / ogg / m4a / aac / opus / wma。读不出来时面板会说明，不报红。
- 切点拖出音频末尾会被**裁到文件长度**，不报错。
- 段最短 0.06 秒，比这更短会被合并 —— 拖到贴着另一条线时就是这个行为。
- 分段表是**首尾相接**的：所有切点都是相邻两段共用的那条线。旧版拖出来的空洞
  （以及那种 0.06 秒的碎段）在打开工作流时会被自动补齐 / 合并，提示词保留。
- 「分段数据」跟着工作流一起保存，换机器打开时路径会失效，需要重新选音频（切点还在）。

## 节点：分段视频合并（dogking-tools）

### 它解决什么

数字人一次只能生成十几秒，所以音频被切成 8 段、跑 8 次队列。**ComfyUI 不会跨执行
累积输出** —— 每段后面接一个「保存视频」，你得到的就是 8 个独立文件，最后还得手工拼。

这个节点把「累积」放到磁盘上：每段先存成一个临时片段，**最后一段跑完自动拼成一条**。

### 怎么接

```
数字人音频分段 ──段序号────┐
                ──段数──────┤
                ──选区音频──┤（可选，整条选区，不是当前段）
生成视频（该段帧）──图像────┤→ 分段视频合并 ──视频路径──→ 播放 / 保存
```

三个口都从音频分段节点上接，**不用另外去接原音频文件**：`段序号` / `段数` 直接对应，
`选区音频` 就是你在面板上框出来的那一整段（含头尾裁剪）。

### 执行时序

| 执行 | 段序号 / 段数 | 节点做什么 | 完成 |
| --- | --- | --- | --- |
| 第 1 次 | 1 / 8 | 清掉同名旧片段，写 `seg_0001.mp4` | false |
| 第 2~7 次 | 2..7 / 8 | 各写一个 `seg_000N.mp4` | false |
| 第 8 次 | 8 / 8 | 校验 8 个片段齐全 → 合并 → `output/<任务名>_<时间>.mp4` | **true** |

标题栏 badge 跟着变：`3/8 已存 3 段`（蓝）→ `完成 1909 帧`（绿）。

### 输入

| 参数 | 说明 |
| --- | --- |
| **图像** | 这一段生成的帧批次（IMAGE） |
| **段序号** / **段数** | 接音频分段的对应输出口 |
| **fps** | **必须填生成时的真实帧率**（24 就填 24）。填错的话音轨时长对不上，表现为越播越偏 |
| **任务名** | 同一个任务名共用一套临时片段；换项目时改个名字即可 |
| **音频**（可选） | **接音频分段的「选区音频」口** —— 那一口就是整条选区（含你框的头尾裁剪），不用另外去接原音频。合并时压成 AAC 写进 mp4；不接就是无声视频 |
| **开始时清空旧片段**（默认开） | **段 1 开始前**清掉同名任务的旧片段，避免上一轮残留混进来 |
| **合并后保留片段**（默认关） | **最后一段合并完成后**留着这一轮的片段；排查接缝问题时会用到 |

> 这两个开关管的是**不同时间点**（开头 / 结尾），不是互斥关系，两个都开也正常：
> 开跑前清掉上一轮的，跑完留着这一轮的。

### 输出

| 输出口 | 类型 | 说明 |
| --- | --- | --- |
| **视频路径** | STRING | 没合并时是当前片段路径，合并后是完整片路径（绝对路径，可直接播） |

合并完成后**节点上会直接显示成片预览**（自动循环播放，和官方 Save Video 一样），
不用另接一个播放节点。中间段不显示，因为还没成片。
| **完成** | BOOLEAN | 最后一段跑完为 true，可以接条件节点触发后续 |
| **总帧数** | INT | 这一段 / 整条的帧数 |

### 注意

- **段序号必须连续**。少一段直接报错并指出缺第几段，绝不输出「能播但短一截」的半成品。
- **音轨会按成片长度截断**。成片时长由帧数决定（17N+5 取整后总比音频差几帧），
  不截的话末尾会拖一段「画面停住、声音还在走」。音频比画面短时正常，不加静音。
- **所有段的分辨率必须一致**。不一致会在合并那一步报中文错误（不会悄悄拼出黑边）。
- 拼接是**重编码**：中间片段 crf 14、成片 crf 16。不用 `-c copy` 是因为 PyAV 17 在 mp4
  上做 packet remux 会报 `Invalid argument`，调外部 `ffmpeg.exe` 又要依赖机器路径。
  两次 crf 16 以内压缩，肉眼看不出来。
- 临时片段在 `output/dogking_concat/<任务名>/`，合并成功后自动清理。
- 每段还会顺手存一份 **`seg_000N_tail.mkv`**（ffv1 + bgr0，末 39 帧**数学无损**），
  专门给「上一段末帧续接」读。段 mp4 是 crf14 有损的，拿它当引导帧等于每段多背一层压缩，
  8 段链上背景纹理最先烂。1344×768 下约 1.6MB/帧、整份 65MB/段，合并后随目录一起清掉。
- **单段模式（段数 = 1）不碰这个目录**，直接输出独立文件 —— 调某一段时不会把
  正在跑的 8 段任务清掉。
- 中途失败重跑：从第 1 段开始会自动清空；只补某一段就直接重跑那一段，最后一段再合并。

## 节点：上一段末帧续接（dogking-tools）

### 它解决什么

H3 分段生成时，段与段之间靠「上一段最后 5 帧」续接（`MiniMaxH3AddGuide` 把这几帧锚在
新段的第 0 帧上）。麻烦在于：**这 5 帧不在这次执行里**，它躺在上一段已经落盘的 mp4 里。

如果图省事把当前采样的 `VAEDecode` 输出接回同一个 `BasicGuider`，ComfyUI 会直接报
**「无效工作流：工作流存在循环节点连线」** —— 那等于用自己还没算出来的结果引导自己，
而且这个校验发生在**执行前的静态拓扑检查**，把开关设成 false 也绕不过去。

这个节点把「上一段末帧」变成一条合法的、来自当前执行之外的输入：

```
段序号 = 5 → 读 output/dogking_concat/<任务名>/seg_0004.mp4 的最后 N 帧
```

### 怎么接

```
数字人音频分段 ──段序号──┐
                ──段数────┤→ 上一段末帧续接 ──末帧─────→ 循环体子图的 image
                                     ──有上一段──→ 循环体子图的 switch
```

`有上一段` 直接替换原来 `a > 1 and b != 1` 那个算式：段序号为 1、上一段没落盘、
或者段数 = 1（单段模式）时都是 False，下游 switch 走「不引导」分支。

### 输入

| 参数 | 说明 |
| --- | --- |
| **段序号** | 接音频分段的「段序号」口；节点读**段序号 − 1** 那一段 |
| **任务名** | 必须和「分段视频合并」的任务名一致，否则找不到片段目录 |
| **取末帧数**（默认 5） | H3 的引导片段只认 **17k+5**：5、22、39、56…。填别的会自动**向下对齐**（填 17 实际按 5 帧用），状态行会写出来 |
| **片段根目录**（默认空） | 留空 = `output/dogking_concat`；填了就当存放各任务子目录的根 |
| **缺段时**（默认黑帧占位） | 只管「段 2 以后、上一段文件不在」：黑帧占位 = 跳过引导照常跑，报错 = 直接停下。**第 1 段和单段模式不受此项影响**（本来就没有上一段，选报错也不会抛） |
| **段数**（可选，默认 0） | 接音频分段的「段数」口。填 1 时**强制不续接** —— 单段模式是在调某一段，磁盘上的 `seg` 文件属于上一轮，接上去画面是错的。留 0 = 不判断 |

### 输出

| 输出口 | 类型 | 说明 |
| --- | --- | --- |
| **末帧** | IMAGE | 上一段最后 N 帧（N ≤ 取末帧数）；无上一段时是 1 帧纯黑占位 |
| **有上一段** | BOOLEAN | 接循环体子图的 switch；False = 不引导 |
| **来源** | STRING | 实际读到的文件路径，接 Display Any 就能看到读的是哪一段。有 `_tail.mkv` 时读它（状态行会写「无损」），没有才退回 mp4 |
| **帧数** | INT | 实际取到的帧数 |

节点上会显示取到的那一帧预览（存 `output/dogking_prev/`），接缝有问题时先看这里。

### 接缝还是会跳：引导帧被裁掉了，它管不了成片接缝

`MiniMaxH3AddGuide` 把引导帧**钉在输出的第 0~21 帧**上，那 22 帧确实和上一段一模一样。
但工作流接着就把这 22 帧裁掉了（`ImageFromBatch start=22`）—— **接缝落在模型裁点后
第一帧「自由发挥」上**，不是落在那 22 帧上。所以引导的作用是「告诉模型从哪儿接着拍」，
不是「让成片接缝平滑」。

实测一条 5×10s 成片（接缝 243/483/723/963）：

| 项 | 数值 | 含义 |
| --- | --- | --- |
| 每段平均亮度 | 110.6 → 109.5 → 107.9 → 104.4 → 101.6 | 逐段掉 **8%**，接缝处就是「暗一下」 |
| 每段平均锐度 | 17.99 → 16.23 → 15.67 → 14.97 → 14.73 | 逐段**变软**（当时开着去锐化 0.35，该功能已移除） |
| 接缝后首帧 vs 稳定值 | 114.9→109.0 / 110.0→105.7 / 106.4→101.1 | 每段开头几帧偏亮，再落回去 |

亮度漂移是模型自己的（上一版没做任何处理也掉 5.5），跟引导帧操作无关。

合并端**不做任何逐段校色** —— 「逐段颜色匹配」已于 2026-11-20 移除（用户实测观感
「非常恐怖」：段与段的色调被硬拽，接缝处像换了个灯）。每段画面原样拼接，跨段的
亮度/色调漂移属内容差，不在合并端处理。

另外合并时会自动压平**段首第 0 帧的过冲**：模型在「引导段结束后的第一个自由生成帧」会画亮
（实测 +2.0~+8.6 个灰度级，而且比引导帧本身还亮 —— 是冲过头，不是被拉过去），第 1 帧自己回落。
做法是把第 0 帧先扣住，等第 1 帧解出来，按它的实测亮度做一次加性偏移 —— 只有这一帧，第 1 帧
及之后一帧不动，首段跳过（它没有引导帧）。开关在代码里（`FIX_HEAD_OVERSHOOT`），不挂 UI。

**整个接缝的影调差不做补偿**，跨段那一档原样留着。

### 音画对齐：为什么「前置重叠帧」必须等于裁剪起点

H3 的音频分支是 `SetLatentNoiseMask(0)` **锁死的原声**，时间轴以音频为准。
而续接把上一段的最后 N 帧钉在输出第 0~N−1 帧上，模型从第 N 帧才回到本段音频的起点：

```
段 N 生成： [钉住的上一段尾巴 N 帧][本段新内容 ...]
裁剪 N 帧后：[本段新内容 ...]        ← 比音频超前 N 帧
```

**每段超前 N 帧、段段累加**，所以第 2 段开始口型就"快一点"，越到后面越快。
22 帧方案下每段 0.917s，6 段累计 4.6s —— 实测那条 6 段成片的接缝正好是
「内容跳一下 + 一帧偏亮 3.4/255 + 随后 12 帧抖动翻倍」。

修法：让音频也把这段前导带进来 —— `前置重叠帧 = 裁剪起点`。

| 位置 | 值 |
| --- | --- |
| 音频分段 · 前置重叠帧 | 22 |
| 两处 `ImageFromBatch` 裁剪起点 | 22 |
| 续接节点 · 取末帧数 | 22 |

前置后音频长度 = 22 + 480 = 502 帧，正好覆盖「被钉住的 22 帧 + 保留的 480 帧」，
**保留下来的每一帧都有音频驱动**（前置前是 480 < 515，段尾 35 帧其实没有音频，
模型在瞎猜）。改其中一处不改另一处 = 偏移照样存在，三个数必须一起动。

### 接缝跳变是不是「裁掉那 22 帧」造成的？——不是

拿真实的两段文件直测（段 1 的 `_tail.mkv` 无损末 39 帧 vs 段 2 的 `seg_0002.mp4` 前 12 帧）：

| 比较对象 | 平均像素差 |
| --- | --- |
| 段 1 内部相邻帧（自然运动） | 4.5 ~ 7.2 |
| **段 2 第 0 帧 vs 段 1 最后一帧** | **6.1** |
| 段 2 第 0 帧 vs 段 1 倒数第 22 帧 | 19.0 |

段 2 首帧与段 1 末帧的差落在「自然相邻帧」区间里，而且这个差随段 1 末尾索引**单调收敛**
（19.0 → 16.0 → 8.4 → 6.1）。也就是说 **`ImageFromBatch(start=22)` 裁完之后，两边时间上
严丝合缝：没跳帧、没重复、没丢内容。**

所以裁剪是对的，问题在**裁点两侧的影调**是两套：

| 指标 | 段 1 末帧 | 段 2 首帧 | 阶跃 |
| --- | --- | --- | --- |
| 亮度 | 106.3 | 106.9 | +0.6（当时「逐段颜色匹配」还开着；该功能已于 2026-11-20 移除） |
| **锐度** | **18.2** | **15.5** | **−15%** |
| B/R | 0.861 | 0.855 | −0.7% |

−15% 这个数字很说明问题：它正好等于当时设的「去锐化 0.15」（该功能已移除）。引导帧被削掉
15% 的高频，下一段就照着这个偏软的质感往下画，**每段 1:1 传递**。

顺带纠正一件容易误解的事：`AddGuide` 的引导帧**不是硬锁在 latent 上**的。源码里
keyframes 是作为 `cond` 行塞进 `PackedLayout` 的（和参考图同一类 token），属于**软条件**。
所以那 22 帧不是"上一段的逐像素复制"，而是模型按上一段尾巴重画的一版；裁掉它是对的
（不裁就是同一时刻播两遍、还带两次渲染的差异），但也不能指望它在成片里当"过渡带"。

### 锐度怎么查

`python tools/quality_report.py 各段.mp4` 直接看每段的锐度趋势，别靠肉眼猜。

治本的三条（按效果排序，都要你自己权衡）：

1. **段数减半**（8×10s → 4×20s）：循环次数少一半，累积天然减半，是唯一确定有效的
2. **二采重绘起点 0.85 → 0.7**：每段少重画一层；但重绘低了口型会松，要自己试
3. **加图片参考**（`ref_image_1` 接场景图）：锚住构图和质感，减少每段「重新想象」

### 注意

- **任务名只填一处**：本节点和「分段视频合并」必须用同一个任务名，两边各填一次容易漏。
  在画布上放一个 `Text`（PrimitiveString）节点，把两个节点的「任务名」都改成输入口接它，
  以后只改这一个文本框 —— 改名不会漏掉一边。
- **引导帧长度只认 17k+5**，而且 `AddGuide` 是「不合法就往下砍、并取 `image[:n]`」——
  填 17 会被砍到 5，砍的还是**前 5 帧**（第 N−16 到第 N−12 帧），接缝直接差 12 帧。
  节点已经替它对齐好了：填 17 → 按 5 帧取，取的是**最后 5 帧**。
- **要加长引导（22/39）要同时改三处**，缺一个都出错：

  | 改哪里 | 5 帧方案 | 22 帧方案 |
  | --- | --- | --- |
  | 本节点「取末帧数」 | 5 | 22 |
  | 两处 `ImageFromBatch` 的 `batch_index`（去重裁剪起点） | 5 | 22 |
  | 段 2+ 的帧长补偿（`a + 17` 那个节点） | 17 | **34** |

  补偿值 = 多裁掉的帧数 + 原来的冗余。补偿少了 → 裁完不够 `段长×24`，每段会短几帧；
  补偿多了 → 只是多算几帧。15s 段在 22 帧方案下总帧数是 396。
- **第 1 段不会去找 `seg_0000.mp4`**，直接给占位帧 + False，照常能跑。
- 上一段不足 N 帧时给多少用多少，不补帧；少于 5 帧时 AddGuide 会只取第 1 张。
- 只解码、只留末尾 N 帧（边解边丢），1344×768 的 10 秒片段读取约 0.2 秒。
- **重跑上一段之后缓存会自动失效**：`IS_CHANGED` 把目标文件的 mtime + 大小写进签名，
  不会一直吃旧的引导帧。
- 单段模式（段数 = 1）**必须不续接**，理由见上表。

## 画质体检（排查「越生成越糊 / 变绿 / 有块」）

肉眼在 1:1 看灰墙一定会觉得糊，靠感觉改参数很容易改错方向。这个脚本把三件事拆成数字：

```bash
python tools/quality_report.py output/dogking_concat/<任务名>/seg_0001.mp4
```

输出首帧 / 25% / 50% / 75% / 末帧的 **亮度、G/R、B/R、饱和、中央锐度、16px 块比**，并给结论：

| 指标 | 怎么读 |
| --- | --- |
| **G/R、B/R** | 同一条片子里应该基本恒定。**越往后越偏**才是颜色漂移；恒定但偏离 1 只是白平衡 |
| **基线锐度** | 去掉开头 12 帧收敛段后的全片均值 ± 标准差。**跨文件比它**才知道改参数有没有用 |
| **波动** | 标准差 ÷ 均值。>12% 才是「忽清忽糊」；7% 以内正常 |
| **块比** | 16px 网格边界落差 ÷ 非边界落差。>1.3 才有量化块效应，1.0 左右正常 |

> ⚠️ **别用「首帧 vs 末帧」判断衰减**。实测 20 秒片段开头 12 帧是模型收敛过程
> （锐度 25.2 平滑降到 17.7），之后 470 帧稳定在 18.7±1.3 —— 拿首帧比末帧会得出
> 「掉 29%」的假结论。脚本已经自动跳过收敛段，只看基线和波动。

多个文件并排跑就能量化对比（换 VAE / 改 sigmas 前后各跑一次），末尾会直接排出基线高低。

## 状态存在哪

`dogking-tools/state.json`，按节点 id 记录每个节点的进度：

```json
{
  "12": { "path": "C:/.../prompts-100.txt", "mode": "全部生成", "index": 5 },
  "220": { "kind": "image", "folder": "D:/pics", "sort": "数字升序", "mode": "全部模式", "index": 5 },
  "301": { "kind": "pv2", "sel": "9f2c1a7b3e04", "index": 3, "total": 12, "ts": 1762700000 }
}
```

三类节点共用这个文件（节点 id 全局唯一，不会冲突）：提示词节点的记录**没有 `kind`**，
图片批量加载节点带 `kind: "image"`，图片+提示词节点带 `kind: "pv2"`，互不干扰。

> **`pv2` 记录里只有 12 位指纹 `sel`，没有清单本身。**
> 清单存在工作流的隐藏 widget（`已选`）里，`state.json` 只存 `sha1("|".join(ids))[:12]`，
> 用来判断「这次执行看到的清单和上次推进时是不是同一份」—— 不是就归零。
> 这样不会出现「两份真相对不上」。
>
> 指纹用的是**原始清单**（不是过滤掉失效项之后的那份），所以
> **PromptVault 里删掉某张图不会让排队进度归零**；而迭代范围用有效张数，
> 失效的图不会在尾部吐出灰帧。

重启 ComfyUI 后进度还在。换文件 / 换文件夹 / 换排序 / 换模式都会自动清零；
PromptVault 节点在**清单变了**（重新选过图）时归零。

想全部重置就删掉这个文件。
